How to tell if your mobile app is leaking its LLM/AI API key

If your iOS or Android app calls OpenAI, Anthropic, or Google directly from the device, there's a real chance the key is visible to anyone watching the traffic — and that's an uncapped bill waiting to happen.

By Igor Ganapolsky · mobile + production-LLM security engineer · updated July 2026

In June 2026, researchers at Wake Forest University published a study that intercepted the network traffic of 444 AI-powered iOS apps. 282 of them — 64% — were leaking exploitable LLM API credentials across ten-plus providers. Only 28% fixed it after being told. Health & Fitness apps were the worst, at a 47% leak rate.

The reason is simple and common: to ship an AI feature quickly, a developer puts the provider API key in the app and calls the model directly from the phone. It works in testing. But a mobile app is not a trusted environment — the key ships inside the binary and rides along in the network request, where it can be read.

Why a leaked key is worse than it sounds

An exposed LLM key isn't a normal secret. It maps directly to spend. An attacker who extracts it can run their own traffic through your provider account — reselling access, mining, or just abusing it — and the first you'll hear about it is the invoice. Documented incidents have burned tens of thousands of dollars in a single day before anyone noticed. This is why it's treated as a critical-severity issue, not a hygiene nit.

The three ways mobile apps leak LLM keys

The Wake Forest study grouped the leaks into three patterns. Almost every real-world case is one of these:

1. Plaintext key transmission

The provider key is sent straight from the device, usually in an Authorization: Bearer … header to api.openai.com, api.anthropic.com, and so on. Anyone who can see the traffic sees the key. This is the most direct and most dangerous pattern.

2. Unauthenticated backend proxy

The team did the right first step — they moved the key to their own server. But the endpoint that forwards prompts to the model doesn't check who is calling it. So anyone can hit that URL directly and use your model budget without ever needing the key. This one fools people because it feels secure.

3. Replayable tokens

A session or bearer token that never expires and isn't bound to a device. If it's captured, it can be replayed indefinitely. Lower severity than the raw key, but it widens the window for everything else.

How to check your own app

You can reproduce roughly what the researchers did, on an app you own, in an afternoon. At a high level:

  1. Put a proxy between the app and the internet. Tools like mitmproxy or Proxyman intercept HTTPS traffic on a device you control. Install the proxy's CA certificate on a test device and route the device's Wi-Fi through it.
  2. Get past certificate pinning if present. Many apps pin certificates, which rejects your proxy. On a device you own, a tool like Frida (often via objection) can disable pinning at runtime so you can see the traffic.
  3. Exercise the AI features and read the requests. Trigger every feature that calls a model, then scan the captured requests — headers, bodies, and query strings — for provider key formats: sk-… (OpenAI), sk-ant-… (Anthropic), AIza… (Google), and bearer tokens.
  4. Also grep the build. Unzip the IPA/APK and search the binary, config files, and any JavaScript bundle (React Native apps often ship keys straight in main.jsbundle).

Do this only on an app you own or are authorized to test. Intercepting an app you don't control is a legal problem, not a research exercise.

How to fix each pattern

  • Get the key off the device. The client should never hold a provider key. Route model calls through your own backend, which holds the key server-side. This is the "zero secrets on the client" pattern.
  • Authenticate the proxy. Your backend model endpoint must verify an authenticated app session, rate-limit per user, and refuse to forward arbitrary requests.
  • Rotate anything that leaked, immediately, and set a hard spend cap on the provider account so any lingering exposure is bounded while you fix the root cause.
  • Use short-lived, device-bound tokens instead of long-lived bearer tokens, and revoke on anomaly.
  • Re-test after the fix — a fresh traffic capture that shows no key or token leaking is the proof you want on file.
