Mobile & AI Security Snapshot — sample report

Example target: "NutriSnap" — a fictional iOS calorie-tracking app with an AI food-photo feature. Assessment method: authorized network-traffic analysis, no source code required.

Executive summary

The app transmits a live third-party LLM API key in outbound traffic and routes some model calls through an unauthenticated backend endpoint. Either issue lets an outside party spend against the provider account. Estimated exposure: uncapped provider billing until the key is rotated. Overall risk: Critical. All findings are remediable in days; a fix plan is included.

Findings

F-1 · Live LLM API key transmitted in plaintext headers (Critical)

During normal use the app sends an LLM provider API key in an Authorization header directly from the device. Anyone able to observe the app's traffic (a shared network, a proxy, a jailbroken device) can read it and use it.

Evidence (redacted)

Authorization: Bearer sk-****…**** → api.<provider>.com/v1/chat/completions, key confirmed live via a $0 read-only metadata call (never a billable request).

Impact

Full use of your provider account on your bill. High-volume abuse can exhaust a five-figure monthly budget in under a day.

Fix

Remove the key from the client entirely. Route model calls through your backend, which holds the key server-side; rotate the exposed key immediately; add a provider spend cap.

F-2 · Unauthenticated model proxy endpoint (High)

A backend route that forwards prompts to the LLM accepts requests without authenticating the caller. Even after the key moves server-side (F-1), this endpoint lets anyone use your model budget by calling it directly.

Fix

Require an authenticated app session on the proxy; add per-user rate limiting and abuse monitoring; scope what the proxy will forward.

F-3 · Long-lived bearer token without rotation (Medium)

A session token observed in traffic does not expire and is replayable if captured. Lower severity than the key itself, but it widens the window of any interception.

Fix

Short-lived tokens with refresh; bind tokens to device/session; revoke on anomaly.

Remediation plan

  • Day 0: Rotate the exposed key; set a provider spend cap so any lingering exposure is bounded.
  • Days 1–3: Move the key server-side behind an authenticated proxy (the "Zero Secrets" pattern); remove it from the client build.
  • Days 3–5: Add proxy auth + rate limiting; move to short-lived tokens; re-test.
  • Re-test: A fresh traffic capture confirming no key or token leaks — the before/after proof you can show your team or an acquirer.
